ticketbench: runbook

Jak przeprowadzić benchmark PostgreSQL 17, MariaDB 11.8, MongoDB 8.0 i Valkey 8.1 programem ticketbench.sh: od pustej maszyny do tabel, wykresów i PDF ze sprawozdaniem. Autorzy: Łukasz Ryczko, Łukasz Pacholec.

1. Szybki start

git clone --recursive https://github.com/ryczek02/ticketbench
cd ticketbench
./ticketbench.sh all        # sprawdzenie, instalacja, start stosu, smoke test
./ticketbench.sh bench      # pełna macierz (0,5 mln, 1 mln, 10 mln biletów)
./ticketbench.sh report     # tabele, wykresy, report/sprawozdanie.pdf

Bez klonowania: pobierz sam skrypt, a on sklonuje repozytorium do ./ticketbench.

curl -fsSLO https://raw.githubusercontent.com/ryczek02/ticketbench/main/ticketbench.sh
chmod +x ticketbench.sh
./ticketbench.sh all

Wszystko to sprawdza jedno polecenie:

./ticketbench.sh doctor

Każda linia z ! wymaga uwagi. Pamięć Dockera na macOS ustawia się w Docker Desktop: Settings → Resources → Memory.

3. Instalacja

./ticketbench.sh install

Polecenie:

  1. klonuje albo aktualizuje repozytorium ticketbench i jego submoduły (contracts, services, cli, infra);
  2. pobiera tbench dla bieżącego systemu z GitHub Releases i sprawdza sumę SHA-256;
  3. pobiera obrazy serwisów z ghcr.io/ryczek02/ticketbench-* oraz obrazy baz.

Warianty:

PolecenieKiedy
TB_CHANNEL=edge ./ticketbench.sh installnajnowszy tbench zbudowany z main
TB_VERSION=0.1.0 ./ticketbench.sh installobrazy konkretnej wersji zamiast latest
TB_UPDATE=1 ./ticketbench.sh installsubmoduły na najnowszy main zamiast przypiętych commitów
TB_SOURCE=1 ./ticketbench.sh installbudowanie obrazów i tbench ze źródeł (wymaga Go 1.26)

Binarki serwerów (np. do uruchomienia bez Dockera) są w wydaniach ticketbench-services: <serwis>_<wersja>_<os>_<arch>.tar.gz.

4. Uruchomienie środowiska

./ticketbench.sh up

Startuje 4 bazy, 4 serwisy store-*, bench-runner, kolektor OpenTelemetry, Jaeger, Prometheus i Grafanę, czeka na kontrole zdrowia i wywołuje tbench ping. Poprawny wynik wygląda tak:

STORE     ADDRESS              STATUS  SERVER                         STRATEGIES
mariadb   store-mariadb:7002   ok      MariaDB 11.8.x                 cond,forupdate,nowait,serializable
mongo     store-mongo:7003     ok      MongoDB 8.0.x                  atomic,txn
postgres  store-postgres:7001  ok      PostgreSQL 17.x                cond,forupdate,nowait,serializable
valkey    store-valkey:7004    ok      Valkey 8.1.x                   lua,setnx,watch

Stan w dowolnej chwili: ./ticketbench.sh status, ./ticketbench.sh ping, adresy interfejsów: ./ticketbench.sh urls.

5. Smoke test

./ticketbench.sh smoke

20 tys. biletów, wszystkie 27 scenariuszy z indeksami i bez, plany zapytań, współbieżność 1 i 16 klientów każdą strategią. Trwa około minuty. Na końcu skrypt wypisuje ścieżkę wyników i powinien pokazać 0 errors oraz contention: 0 inconsistent groups. Jeśli smoke test przechodzi, środowisko jest gotowe do pełnej macierzy.

6. Pełna macierz

./ticketbench.sh bench

Plan z infra/config/matrix.yaml:

  • 3 rozmiary: 500 tys., 1 mln i 10 mln biletów;
  • 4 bazy, każda z czystym importem danych;
  • 27 scenariuszy, 1 przebieg rozgrzewkowy i 5 mierzonych, bez indeksów i z indeksami;
  • plany zapytań (EXPLAIN ANALYZE, explain executionStats);
  • współbieżność: 1, 10, 100 i 1000 klientów na tych samych 500 miejscach, każda strategia, 3 rundy;
  • pomiar narzutu śledzenia na 500 tys. biletów.

Na Apple M5 z 8 GB dla Dockera cały plan trwał około 1,5 godziny. Najdłużej trwają scenariusze Valkey bez indeksów na 10 mln (pełny SCAN) i współbieżność MariaDB przy 1000 klientach.

Zawężanie planu (flagi idą prosto do tbench matrix):

./ticketbench.sh bench --sizes 500k,1M
./ticketbench.sh bench --stores postgres,valkey
./ticketbench.sh bench --config moja-macierz.yaml

Podgląd kroków bez uruchamiania: tbench plan --config infra/config/matrix.yaml (binarka leży w bin/tbench).

Wyniki zapisują się na bieżąco. Przerwany przebieg zostawia wszystko, co zdążył zmierzyć. Brakujący segment można powtórzyć osobno, a tbench report przyjmuje kilka katalogów wyników naraz.

7. TLS i ograniczone role

./ticketbench.sh security

Przełącza stos na nakładkę infra/docker-compose.security.yml, czyli TLS we wszystkich bazach z własnym CA (certyfikaty generuje kontener certs) i konta aplikacyjne z samym DML:

  • PostgreSQL: rola tb_app z SELECT, INSERT, UPDATE, DELETE;
  • MariaDB: użytkownik tb_app z tymi samymi uprawnieniami;
  • MongoDB: uwierzytelnianie i rola find/insert/update/remove;
  • Valkey: użytkownik ACL tbapp bez poleceń @admin i @dangerous, tylko prefiksy kluczy modelu.

Na 1 mln biletów każda baza jest ładowana raz przez administratora, a potem wszystkie scenariusze i test współbieżności (1 i 100 klientów) przechodzą przez cztery profile połączenia: base, role, tls i tls_role. Wyniki trafiają do results/security-latest, a ./ticketbench.sh report dołącza je do sprawozdania (tabela narzutu w procentach względem base). Ten wariant używa osobnych wolumenów, więc dane głównej macierzy zostają nietknięte. Powrót do zwykłego stosu: ./ticketbench.sh up.

8. Pojedyncze pomiary

# wybrane scenariusze na jednej bazie, z importem danych
./ticketbench.sh run --stores postgres --tickets 1M --scenarios R4,U6 --reps 10 --indexes both

# na już załadowanych danych
./ticketbench.sh run --stores mongo --tickets 1M --scenarios 'R*' --load=false

# tylko test współbieżności, wszystkie strategie
./ticketbench.sh contend --stores mariadb,valkey --tickets 500k --clients 1,10,100,1000 --strategies all

# lista scenariuszy
bin/tbench scenarios

9. Raport i PDF

./ticketbench.sh report                      # ostatni przebieg (results/latest)
./ticketbench.sh report results/20261121-220002

Polecenie generuje report/generated/ (tabele LaTeX, dane wykresów pgfplots, makra z werdyktami hipotez, values.tex z każdą zmierzoną wartością), kopiuje surowe wyniki do report/data/results i kompiluje report/sprawozdanie.pdf, report/prezentacja.pdf (slajdy) oraz report/podsumowanie.pdf, jeśli jest tectonic albo latexmk. Liczby w sprawozdaniu pochodzą wyłącznie z tych plików, a CI sprawdza, czy zgadzają się z surowymi wynikami.

11. Śledzenie i metryki

  • Jaeger (localhost:16686): każdy segment (rozmiar × baza) to jeden ślad. Identyfikator jest w każdym wierszu CSV, więc wolne powtórzenie otwiera się pod http://localhost:16686/trace/<trace_id>. W śladzie widać span CLI, kroki runnera, wywołania Execute, spany serwisu i polecenia SQL, MongoDB lub Valkey.
  • Grafana (localhost:3000, pulpit ticketbench): p95 czasu scenariuszy per baza, czas prób rezerwacji, konflikty na sekundę.
  • Prometheus (localhost:9090): metryki tb_store_scenario_duration_milliseconds, tb_store_contention_attempt_milliseconds, tb_store_contention_conflicts_total.

12. Sprzątanie

./ticketbench.sh down       # zatrzymuje kontenery, dane zostają
./ticketbench.sh destroy    # usuwa kontenery i wolumeny baz

Wyniki w results/ i pliki raportu zostają.

13. Rozwiązywanie problemów

ObjawPrzyczyna i rozwiązanie
bind: address already in use przy starcieport zajęty przez inną usługę. ./ticketbench.sh doctor pokazuje które. Port runnera zmienia TB_RUNNER_PORT=7171.
store-mongo długo niezdrowypierwszy start inicjuje replica set rs0. Kontrola zdrowia robi to sama, zwykle w 10–20 s. Podgląd: ./ticketbench.sh logs mongo.
Kontener bazy znika w trakcie 10 mln (OOMKilled)za mało pamięci dla Dockera. Zwiększ do 10 GB albo uruchom bench --sizes 500k,1M.
„t/o” w tabeliscenariusz przekroczył 60 s (zwykle Valkey bez indeksów na dużych zbiorach). To wynik, nie awaria. Limit zmienia timeout: w pliku macierzy.
tbench: connection refusedstos nie działa albo runner jest na innym porcie: ./ticketbench.sh up, sprawdź TB_RUNNER_PORT.
Brak PDF po reportbrak tectonic i latexmk. Instalacja: brew install tectonic albo apt install latexmk texlive-xetex texlive-lang-polish.
Pobieranie tbench kończy się błędem 403limit zapytań do API GitHuba bez logowania. Odczekaj godzinę albo zbuduj ze źródeł: TB_SOURCE=1.
